# GOAL — 2026-09-28

## Objective

Make **Pi the primary/default Hivemind runtime** and give every configured agent a persistent Pi RPC process across chat turns.

Hivemind is the orchestrator. Pi is the lightweight execution harness. Do not make Hivemind depend on OMP-specific behavior.

## Why this is the next step

The current POC already proves:

- Rust CLI orchestration,
- multiple configured agents,
- concurrent fan-out of one user turn,
- runtime adapter boundaries,
- per-agent workspace/model/reasoning configuration.

However, the current implementation is centered on OMP and creates disposable runtime processes. Before adding spawning, agent-to-agent messaging, tasks, or memory, establish the smaller baseline:

```text
Hivemind -> persistent Pi agents
```

Pi should become the first-class runtime because the goal of Hivemind is to own orchestration while keeping the underlying agent harness as lightweight as practical.

## Target architecture

```text
Hivemind CLI
    |
Agent / Runtime Manager
    |
    +-- Maomao
    |     -> persistent Pi RPC process
    |
    +-- Albedo
          -> persistent Pi RPC process
```

Each Hivemind agent owns exactly one Pi RPC process for the lifetime of the chat session.

Different agents may execute concurrently, but prompts sent to one agent must be processed sequentially through that agent's own RPC stream.

## Pi integration

Use Pi's subprocess RPC interface:

```bash
pi --mode rpc
```

Hivemind is written in Rust, so prefer Pi's language-agnostic JSONL RPC protocol over embedding the TypeScript SDK.

The Pi adapter must:

1. Spawn one `pi --mode rpc` process per Hivemind agent.
2. Set the process working directory from the agent's `workspace`.
3. Apply configured model and reasoning/thinking options at startup.
4. Apply the agent system prompt using Pi-supported CLI/runtime configuration.
5. Wait until the Pi RPC process is ready before sending work.
6. Send every later user turn to that same live process.
7. Correlate RPC responses/events correctly.
8. Return the final assistant response to Hivemind.
9. Shut Pi down cleanly when Hivemind exits.
10. Never leave orphan Pi processes.

Use `--no-session` if appropriate so Hivemind owns lifecycle/persistence rather than Pi writing durable session state. The live process must still retain conversation context across turns.

## Runtime abstraction

Do not couple the CLI directly to Pi.

Refactor toward a persistent runtime-neutral session boundary, conceptually:

```rust
trait HarnessSession {
    async fn prompt(&mut self, input: &str) -> Result<String>;
    async fn shutdown(&mut self) -> Result<()>;
}
```

The concrete API may differ. Keep the contract small enough that OMP, Codex, Claude Code, or another harness can be added later without changing Hivemind's agent model.

## Configuration changes

Make Pi the default runtime.

A target configuration should resemble:

```toml
[runtime]
pi_binary = "pi"

[[agents]]
name = "Maomao"
runtime = "pi"
workspace = "."
system_prompt = "You are Maomao."

# optional
model = "provider/model-id"
reasoning = "high"
```

Do not invent a Pi equivalent for OMP-only options.

In particular, if Pi does not expose an OMP-style `fast` switch, the Pi adapter must not pretend that it does.

If retaining the existing OMP adapter is cheap and does not complicate the migration, it may remain as a secondary adapter for compatibility. It must no longer be the default or architectural center of Hivemind.

## Persistent behavior

Example acceptance flow:

```text
Hivemind starts
  ├─ Maomao -> Pi process/session A
  └─ Albedo -> Pi process/session B

You> hello, remember the word pineapple
  ├─ session A receives the turn
  └─ session B receives the turn

You> what word did I ask you to remember?
  ├─ SAME session A receives the turn
  └─ SAME session B receives the turn
```

The two agents must remember their own conversation state independently.

Do not start a new Pi process for every prompt.

## Failure handling

Keep recovery deterministic for this milestone:

- If Pi is missing or cannot start, report the affected agent and the underlying error.
- If one Pi child dies, surface the failure for that agent.
- Do not silently restart an agent and imply that its conversational context survived.
- One failed agent must not corrupt another agent's RPC stream.
- Clean up all remaining child processes on normal exit and error paths.

Automatic restart/recovery is a later milestone.

## Required existing behavior

Preserve:

- multiple configured agents,
- concurrent execution between different agents,
- agent workspace,
- system prompts,
- per-agent model,
- per-agent reasoning/thinking,
- `/agents`,
- `/help`,
- `/quit`.

## Acceptance criteria

The goal is complete when:

1. Pi is the default runtime generated by `hivemind init`.
2. At least two agents can run through Pi simultaneously.
3. Each agent owns one persistent Pi process across multiple user turns.
4. The "pineapple" two-turn test proves conversational continuity.
5. Agents remain isolated from each other's conversational state.
6. Model/reasoning settings are passed correctly to Pi.
7. Hivemind exits without orphan Pi processes.
8. `cargo test` passes.
9. `cargo clippy --all-targets --all-features -- -D warnings` passes.

## Tests to add

Add tests where practical for:

- Pi CLI/RPC arguments,
- per-agent configuration,
- persistent process reuse,
- ordered prompts for one agent,
- concurrent independent agents,
- RPC error attribution,
- runtime shutdown/cleanup.

Prefer fake process/RPC fixtures over tests that require paid API calls.

## Non-goals

Do **not** implement these in this goal:

- agent-to-agent messaging,
- dynamic agent spawning,
- `<spawn params=...>`,
- subagent orchestration,
- shared memory,
- durable memory database,
- Codex or Claude adapters,
- GUI/TUI,
- remote/distributed workers,
- autonomous task planning.

OMP-specific features are also not requirements for the Pi runtime.

## Definition of done

Hivemind should evolve from:

```text
Hivemind -> disposable OMP invocation per prompt
```

to:

```text
Hivemind
  -> owns agents
  -> each agent owns one lightweight Pi RPC process
  -> process survives across turns
  -> clean shutdown
```

Once this works, the next major milestone is Hivemind-controlled agent communication and dynamic spawning.
