# GOAL — 2026-09-28 — Pi Runtime

## Objective

Add **Pi as a lightweight first-class runtime adapter** for Hivemind without removing the existing OMP adapter.

The purpose of this goal is not to replace OMP immediately. It is to prove that Hivemind can own the agent abstraction while different harnesses sit underneath it.

## Desired architecture

```text
Hivemind
   |
   +-- Agent A -> Pi
   |
   +-- Agent B -> Pi
   |
   +-- Agent C -> OMP
```

An agent belongs to Hivemind. Pi and OMP are runtime implementations.

## Why Pi

Pi should be supported because it is a smaller, lighter harness and fits Hivemind's goal of running multiple agents without making every agent carry unnecessary orchestration overhead.

Hivemind should provide the higher-level orchestration. Pi should provide the lightweight agent execution layer.

## Scope

Implement a new Pi runtime adapter alongside OMP.

The existing OMP implementation must continue to work.

A configuration should be able to select either runtime per agent:

```toml
[runtime]
omp_binary = "omp"
pi_binary = "pi"

[[agents]]
name = "Maomao"
runtime = "pi"
workspace = "."
system_prompt = "You are Maomao."
model = "provider/model-id"
reasoning = "high"

[[agents]]
name = "Albedo"
runtime = "omp"
workspace = "."
system_prompt = "You are Albedo."
```

## Pi integration

Use Pi's CLI/RPC capabilities rather than embedding a TypeScript SDK into the Rust project.

Prefer a subprocess-based RPC design if Pi supports the required conversation/session semantics.

The Pi adapter should:

1. Start Pi from the configured binary.
2. Use the agent's workspace as the working directory.
3. Apply the agent system prompt.
4. Apply configured model and reasoning/thinking settings when supported.
5. Send a user prompt and receive the assistant response.
6. Return a clear error if Pi is missing, exits, or returns malformed output.
7. Keep Pi-specific behavior inside the Pi adapter.

Do not invent mappings for settings Pi does not support.

For example, OMP's `fast` setting is OMP-specific unless Pi has an actual equivalent.

## Runtime abstraction

Keep runtime selection behind the existing Hivemind adapter boundary.

The CLI should not need Pi-specific branching beyond selecting the adapter.

Conceptually:

```text
AgentConfig
    |
runtime = "pi"
    |
Runtime dispatcher
    |
PiAdapter
```

Do not duplicate orchestration logic inside the adapter.

## Configuration

Extend runtime configuration with a Pi binary setting.

Default:

```toml
[runtime]
omp_binary = "omp"
pi_binary = "pi"
```

An agent using:

```toml
runtime = "pi"
```

must execute through Pi.

An agent using:

```toml
runtime = "omp"
```

must continue executing through OMP.

Keep backward compatibility with existing Hivemind configs where practical.

## Required behavior

Preserve existing Hivemind behavior:

- multiple configured agents,
- concurrent fan-out of user turns,
- per-agent workspaces,
- system prompts,
- model selection,
- reasoning configuration,
- OMP support,
- `/agents`,
- `/help`,
- `/quit`.

Mixed runtimes must be possible in one Hivemind process.

## Acceptance criteria

The goal is complete when:

1. Hivemind recognizes `runtime = "pi"`.
2. At least one Pi-backed agent can respond to `hello`.
3. Two Pi-backed agents can respond independently to the same user turn.
4. A Pi agent and an OMP agent can coexist in the same config.
5. Pi uses the configured workspace.
6. Supported model/reasoning options are applied correctly.
7. Unsupported Pi options are not silently fabricated.
8. Existing OMP tests still pass.
9. New Pi adapter tests are added.
10. `cargo test` passes.
11. `cargo clippy --all-targets --all-features -- -D warnings` passes.

## Tests to add

Add tests for:

- Pi command/RPC argument construction,
- runtime dispatch for `runtime = "pi"`,
- Pi binary configuration,
- model/reasoning mapping,
- mixed Pi + OMP agent configuration,
- useful errors for missing or failed Pi processes.

Avoid provider-dependent tests where command/process fixtures can prove the behavior.

## Non-goals

Do **not** implement these as part of this goal:

- replacing/removing OMP,
- persistent cross-turn sessions,
- agent-to-agent messaging,
- dynamic agent spawning,
- `<spawn params=...>`,
- shared memory,
- task delegation,
- GUI/TUI,
- distributed workers,
- autonomous orchestration.

Persistent Pi sessions should be handled as a separate milestone after the adapter itself works reliably.

## Definition of done

The important architectural result is:

```text
Hivemind Agent
      |
      +---- PiAdapter
      |
      +---- OmpAdapter
```

Hivemind must no longer be conceptually tied to one harness.

Pi becomes available as the lightweight runtime foundation we can use for the next milestones.
